CHAPTER 02 — REQUIREMENTS ENGINEERING
جمع المتطلبات
Requirements Engineering
المتطلب هو وصف لما يجب أن يفعله النظام. جمعها بشكل صحيح هو الفرق بين مشروع ناجح ومشروع يُلغى بعد سنة من العمل.

2.1 أنواع المتطلبات

🎯 Functional Requirements

ما الذي يفعله النظام — الوظائف والميزات الأساسية.

مثال: يجب أن يتمكن المستخدم من تسجيل الدخول بالبريد الإلكتروني وكلمة المرور
⚡ Non-Functional Requirements

كيف يؤدي النظام وظائفه — الجودة والأداء.

مثال: يجب أن يستجيب النظام في أقل من 2 ثانية — يدعم 10,000 مستخدم متزامن
نوع المتطلب أمثلة يُقاس بـ
الأداء (Performance) وقت الاستجابة، الإنتاجية ثانية، طلب/ثانية
الأمان (Security) تشفير، صلاحيات، جدار حماية معايير ISO/OWASP
القابلية للتوسع (Scalability) عدد المستخدمين، حجم البيانات عدد المستخدمين
الموثوقية (Reliability) وقت التشغيل، معدل الأعطال 99.9% uptime
قابلية الصيانة (Maintainability) سهولة التعديل والإضافة تقدير الجهد

2.2 تقنيات جمع المتطلبات

1
المقابلات (Interviews)
جلسات مباشرة مع أصحاب المصلحة. الأقوى لفهم الأولويات والمشاعر. اسأل أسئلة مفتوحة: "كيف تعمل حالياً؟" "ما أكبر مشكلة؟"
2
ورش العمل (Workshops)
جمع مجموعات من المستخدمين معاً. تكشف التناقضات بين الأقسام المختلفة وتوفر وقتاً.
3
الملاحظة (Observation)
شاهد المستخدم وهو يعمل. المستخدمون كثيراً ما ينسون يذكروا خطوات اعتادوا عليها.
4
النماذج الأولية (Prototyping)
قدّم نموذجاً مبدئياً. العميل يفهم ما يريد بشكل أوضح عندما يرى شيئاً ملموساً.
5
تحليل الوثائق
ادرس النظام الحالي، الفواتير، التقارير، العقود. تكشف متطلبات خفية كثيرة.

2.3 User Stories — الطريقة الحديثة

📖 صيغة User Story

As a [نوع المستخدم],
I want to [ما يريد فعله],
So that [لماذا / الفائدة].

📱 مثال: تطبيق توصيل طلبات
🛵 كعميل، أريد أن أتتبع طلبي على الخريطة في الوقت الحقيقي، حتى أعرف متى يصل وأكون مستعداً.

👨‍🍳 كمطعم، أريد أن أرى الطلبات الواردة وأقبلها أو أرفضها، حتى أدير طاقتي الإنتاجية بكفاءة.

🚴 كسائق توصيل، أريد أن أرى الطلبات القريبة مني وأختار الأنسب، حتى أزيد دخلي.

3.2 خطوات استخراج الكائنات

1
اقرأ وصف المشكلة

2
ظلّل الأسماء

3

4

CHAPTER 04 — OBJECT RELATIONSHIPS
العلاقات بين الكائنات
Association · Aggregation · Composition · Inheritance
الكائنات لا تعيش بمعزل عن بعضها — تتواصل وتتحكم وترث. فهم هذه العلاقات هو المفتاح لرسم Class Diagrams صحيحة ومعبّرة.

4.1 أنواع العلاقات الأربعة

Association — الارتباط العلاقة الأساسية

علاقة "يعرف" أو "يستخدم". الكائن A يعرف عن كائن B. الأبسط والأكثر شيوعاً.

ASSOCIATION DIAGRAM
طالب يسجّل في مساقات متعددة
PlantUMLAssociation 
@startuml
Student "1" -- "*" Course : enrolls

class Student {
  -name: String
  +enroll()
}

class Course {
  -title: String
  +getStudents()
}
@enduml
Aggregation — التجميع has-a (weak)

علاقة "يحتوي على" — لكن الجزء يمكن أن يستمر بدون الكل. الكائن B يمكن أن ينتمي لكائنات متعددة.

💡التعرّف: لو أتلفنا الـ "الكل" — هل يبقى "الجزء"؟ إذا نعم = Aggregation.
مثال: المعلم يُعطّل القسم، لكن المعلم لا يزال موجوداً.
PlantUMLAggregation — معيّن مفتوح 
@startuml
Department "1" o-- "*" Teacher : has
' o-- يرسم المعيّن الأبيض (Aggregation)

class Department {
  -deptName: String
  +addTeacher()
}
class Teacher {
  -name: String
  -salary: double
}
@enduml
Composition — التركيب has-a (strong)

علاقة "يتكوّن من" — الجزء لا يمكن أن يعيش بدون الكل. إذا أُتلف الكل، يُتلف معه كل أجزائه.

⚠️مثال: الـ House تحتوي على Rooms. لو هدمنا البيت — الغرف لا وجود لها بدونه. هذا Composition.
PlantUMLComposition — معيّن مملوء 
@startuml
House "1" *-- "1..*" Room : contains
' *-- يرسم المعيّن الأسود (Composition)

class House {
  -address: String
  +addRoom()
  +removeRoom()
}
class Room {
  -roomType: String
  -area: double
}
@enduml
Inheritance — الوراثة is-a relationship

الكائن الابن يرث خصائص وعمليات الأب. الابن هو "نوع من" الأب.

PlantUMLInheritance — سهم مجوف 
@startuml
abstract class Animal {
  #name: String
  +{abstract} makeSound(): void
  +eat(): void
}

Dog --|> Animal
Cat --|> Animal
' --|> يرسم سهم الوراثة

class Dog {
  +makeSound(): void
  +fetch(): void
}
class Cat {
  +makeSound(): void
  +purr(): void
}
@enduml
العلاقة الرمز PlantUML المعنى مثال
Association -- يعرف / يستخدم Student — Course
Aggregation o-- يحتوي (ضعيف) Department ◇ Teacher
Composition *-- يتكوّن (قوي) House ◆ Room
Inheritance --|> هو نوع من Dog → Animal
Realization ..|> ينفّذ واجهة Circle → Shape
Dependency .. يعتمد على Order ..> Payment

9.1 مكونات Use Case Diagram

🧑 Actor — الفاعل

كل من يتفاعل مع النظام من الخارج. قد يكون إنساناً أو نظاماً آخر.

⭕ Use Case — حالة الاستخدام

وظيفة أو هدف يريد الفاعل تحقيقه من النظام.

📦 System Boundary

مستطيل يحدد ما هو داخل النظام وما هو خارجه.

CHAPTER 14 — DESIGN PATTERNS INTRODUCTION
أنماط التصميم
Design Patterns — GoF 23
في 1994، أربعة مهندسين (Gang of Four) جمعوا 23 حلاً للمشاكل المتكررة في التصميم البرمجي. هذه الأنماط أصبحت لغة مشتركة بين المطورين حول العالم.

14.1 ما هو نمط التصميم؟

💡 التعريف

نمط التصميم هو حل جاهز وموثّق لمشكلة متكررة في تصميم البرمجيات. ليس كوداً جاهزاً، بل وصف لكيفية حل المشكلة في سياق معين.

🎯تشبيه: أنماط التصميم مثل الوصفات المطبخية — عندك مشكلة معروفة (تريد طبق معين)، والوصفة تعطيك حلاً مجرَّباً ومضموناً.

CHAPTER 15 — CREATIONAL PATTERNS
أنماط الإنشاء
Singleton · Factory · Builder
أنماط الإنشاء تُعالج مشكلة إنشاء الكائنات — متى وكيف وبأي عدد. الغلطة الشائعة: استخدام new في كل مكان دون تنظيم.
Singleton Pattern CREATIONAL · #1
🎯 المشكلة: كائن واحد فقط في التطبيق ✅ الحل: منع إنشاء أكثر من instance

المشكلة: تريد connection واحداً لقاعدة البيانات، أو Logger واحداً في كل التطبيق. لو أنشأت أكثر من instance — ستحدث مشاكل.

PlantUMLSingleton 
@startuml
class DatabaseConnection {
  -{static} instance: DBConn
  -connectionString: String
  -{static} count: int

  -DatabaseConnection()
  +{static} getInstance(): DBConn
  +executeQuery(): ResultSet
  +close(): void
}

DatabaseConnection --> DatabaseConnection
@enduml
SINGLETON STRUCTURE
C++ ImplementationThread-Safe Singleton 
class DatabaseConnection {
private:
    static DatabaseConnection* instance; // instance وحيد
    string connectionString;

    DatabaseConnection() {} // constructor خاص — لا يمكن استدعاؤه من خارج
    DatabaseConnection(const DatabaseConnection&) = delete; // منع النسخ

public:
    static DatabaseConnection* getInstance() {
        if (instance == nullptr) {
            instance = new DatabaseConnection(); // إنشاء مرة واحدة فقط
        }
        return instance;
    }

    void executeQuery(string sql) {
        // تنفيذ الاستعلام
    }
};

// الاستخدام
DatabaseConnection* db1 = DatabaseConnection::getInstance();
DatabaseConnection* db2 = DatabaseConnection::getInstance();
// db1 == db2 — نفس الكائن تماماً! ✅
✅استخدم Singleton عندما: قاعدة بيانات، Logger، Configuration Manager، Thread Pool — أي شيء يجب أن يكون له نسخة واحدة فقط.
⚠️تجنّب Singleton عندما: يجعل الكود صعب الاختبار (Unit Testing)، ويخلق coupling شديداً بين المكونات.
Factory Method Pattern CREATIONAL · #3
🎯 إنشاء كائنات بدون تحديد النوع الدقيق ✅ يتبع Open/Closed Principle

المشكلة: تريد إنشاء أشكال مختلفة (Circle, Rectangle, Triangle) لكن الكود المُستخدم لا يجب أن يعرف النوع الدقيق.

PlantUML — Factory MethodShape Factory

interface Shape {

  +area(): double

abstract class ShapeFactory {
  +{abstract} createShape(): Shape
  +deliverShape(): Shape
}

CircleFactory    --|> ShapeFactory
RectangleFactory --|> ShapeFactory

Circle    ..|> Shape
Rectangle ..|> Shape

CircleFactory    ..> Circle    : creates
RectangleFactory ..> Rectangle : creates
@enduml

CHAPTER 16 — STRUCTURAL PATTERNS
أنماط الهيكل
Adapter · Decorator · Facade
أنماط الهيكل تُعالج كيفية تنظيم الكائنات وتركيبها. تُساعد في بناء أنظمة مرنة يمكن توسيعها وتعديلها بسهولة.
Adapter Pattern STRUCTURAL · المحوّل

المشكلة: عندك مكتبة قديمة بواجهة مختلفة، وكودك الجديد يتوقع واجهة أخرى. تريد أن تجعلهما يتعاملان مع بعض بدون تعديل أي منهما.

🔌تشبيه: محوّل الكهرباء من 220 إلى 110 فولت — يجعل الجهاز الأمريكي يعمل في المقبس المصري بدون تعديل.
PlantUML — AdapterPayment Adapter 
@startuml
interface PaymentProcessor {
  +pay(amount: double): boolean
}

class OldPaymentSystem {
  +makePayment(cents: int): String
  // واجهة قديمة — تقبل سنتات وترجع String
}

class PaymentAdapter implements PaymentProcessor {
  -oldSystem: OldPaymentSystem
  +pay(amount: double): boolean
  // يحوّل double → cents ويحوّل String → boolean
}

PaymentAdapter --> OldPaymentSystem : wraps
Client          --> PaymentProcessor : uses
@enduml
Decorator Pattern STRUCTURAL · المزخرف

المشكلة: تريد إضافة ميزات لكائن موجود ديناميكياً — بدون وراثة وبدون تعديل الكود الأصلي.

☕تشبيه: أمر القهوة — قهوة أساسية + حليب + سكر + كريمة. كل إضافة "تُغلّف" الطلب الأصلي وتضيف له.

  +getDescription(): String

@enduml

المشكلة: نظام معقد يتكون من عشرات الكلاسات. تريد تقديم واجهة بسيطة للعميل بدون إخفاء التعقيد الداخلي كلياً.

CHAPTER 17 — BEHAVIORAL PATTERNS
أنماط السلوك
Observer · Strategy · Command
أنماط السلوك تُعالج كيفية تواصل الكائنات وتوزيع المسؤوليات. هي الأكثر استخداماً في الأنظمة الحديثة.
Observer Pattern BEHAVIORAL · المراقب
📡 Publish-Subscribe 🔔 Event-Driven ✅ Loose Coupling

المشكلة: كائن (Subject) يحتاج أن يُخطر كائنات أخرى (Observers) عند تغيّر حالته — بدون معرفة من هم بالضبط.

📰تشبيه: الاشتراك في قناة يوتيوب. القناة (Subject) تنشر فيديو → كل المشتركين (Observers) يتلقون إشعاراً تلقائياً. القناة لا تعرف من هم المشتركون بالاسم.
PlantUML — ObserverStock Market System 
@startuml
interface Observer {
  +update(stockPrice: double): void
}

interface Subject {
  +addObserver(o: Observer): void
  +removeObserver(o: Observer): void
  +notifyObservers(): void
}

class StockMarket implements Subject {
  -observers: List~Observer~
  -currentPrice: double
  +setPrice(price: double): void
  +notifyObservers(): void
}

class MobileApp implements Observer {
  +update(price: double): void
}
class WebDashboard implements Observer {
  +update(price: double): void
}
class EmailAlert implements Observer {
  +update(price: double): void
}

StockMarket --> Observer : notifies
@enduml
Strategy Pattern BEHAVIORAL · الاستراتيجية

المشكلة: تريد تغيير خوارزمية أو سلوك كائن في وقت التشغيل بدون تعديل الكلاس الأصلي.

🗺️تشبيه: Google Maps — نفس التطبيق، لكن يمكن تغيير استراتيجية التنقل: سيارة، مشياً، دراجة، وسائل نقل عام. كل استراتيجية خوارزمية مختلفة.

class Flight {

  +refund(): boolean

🎯 أسئلة مراجعة — المشروع الكامل
لماذا اخترنا Strategy Pattern للدفع بدلاً من if-else؟ — لأن طرق الدفع قد تتغير مستقبلاً. Strategy يتبع Open/Closed Principle
لماذا Observer للإشعارات؟ — Flight لا يجب أن يعرف كل من يريد الإشعارات. Observer يفصل المنطق
أين نستخدم Singleton هنا؟ — في Database Connection Manager وفي الـ Logger
كيف نضيف طريقة دفع جديدة (Crypto)؟ — فقط أنشئ كلاس جديد يُنفّذ PaymentStrategy. لا تعديل في الكود القديم
